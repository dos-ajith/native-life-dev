# Native Life API — Project Rules

Backend for a mobile app + web admin panel. Python 3.12, FastAPI, PostgreSQL,
SQLAlchemy 2.x, Alembic, Pydantic v2, JWT auth. Modular monolith — no
microservices, no Redis/Celery/Kafka/Kubernetes unless a real requirement
appears (don't add infra speculatively).

The user is an experienced Laravel/PHP developer, new to this stack. When
explaining changes, brief Laravel comparisons are welcome, but code itself
should just be good Python — don't shape the code around the comparison.

## Non-negotiable rules

1. **Never hardcode secrets, keys, URLs, or credentials.** Everything
   configurable lives in `.env` (local) and is read through
   `app/core/config.py`'s `Settings` (pydantic-settings). If a value might
   differ between environments (DB URL, JWT secret, CORS origins, third-party
   API keys, feature flags), it's a `Settings` field with no insecure
   default — never a literal in code.
2. **Never edit `.env.example` with real values.** It's the committed
   template with placeholders only. Real values go in `.env`, which is
   gitignored. If you ever see a real secret land in `.env.example`, fix it
   immediately and check `git status`/`git diff` before any commit.
3. **Never commit `.env`.** Check `git status` before staging broadly.

## Architecture — layering

```
Router (app/api/v1/<module>/)   -- thin: HTTP in/out, calls a service, returns
    -> Schema (app/schemas/)     -- Pydantic request/response validation
    -> Service (app/services/)   -- business logic, transactions, rules
    -> Repository (app/repositories/) -- DB queries only
    -> Model (app/models/)       -- SQLAlchemy ORM tables
```

- Routers never contain business logic, raw SQL, password hashing, or
  transaction logic.
- Repositories never contain business rules — just persistence/query concerns.
- Skip the repository/service split only for genuinely trivial CRUD, and say
  explicitly why when doing so — don't apply it silently as a shortcut.
- Adding a new module (e.g. `products/`) must not require modifying unrelated
  modules, except one `include_router(...)` line in `app/api/v1/router.py`.
- Mobile and admin endpoints share the same service layer where the business
  logic is identical; only authorization/presentation differs.

## Coding standards

- Type hints everywhere; code should pass `ruff check .` and `mypy app`
  cleanly before considering a change done.
- Small, single-responsibility functions/classes. No giant service classes.
- Composition over inheritance unless inheritance clearly fits (e.g. the
  `AppError` exception hierarchy, SQLAlchemy's declarative `Base`).
- No speculative abstractions, feature flags, or "future-proofing" for
  requirements that don't exist yet. Three similar lines beat a premature
  abstraction. Every pattern introduced must solve a problem that exists now.
- No global mutable state, no magic values (use named constants/settings).
- **No comments in the codebase, including docstrings.** Code must be
  self-explanatory through naming and structure. If something genuinely
  needs explaining, put it in the PR description or commit message, not in
  the file.

## Database & migrations

- All schema changes go through Alembic migrations, committed to git.
  Never hand-edit a production schema.
- Always review autogenerated migrations before applying them.
- Never edit an already-applied migration to rewrite history — create a new
  migration to fix a previous one.
- Be deliberate about destructive changes (dropping columns/tables); for
  anything beyond local dev, prefer safe multi-step migrations.
- UUID primary keys, `created_at`/`updated_at` timestamps, explicit
  nullability, and foreign keys are the default for new tables. Don't add
  soft-delete, indexes, or check constraints unless there's a concrete reason
  — state the reason when adding one.

## API conventions

- All routes versioned under `/api/v1/...`.
- Success responses return the resource/schema directly — no envelope.
- Error responses always use: `{"success": false, "message": "...", "errors": [...]}`.
- Pagination, filtering, and sorting use the shared reusable utilities/schemas
  once introduced — don't reimplement per-module.
- Authentication ("who is this user?") and authorization ("can they do this?")
  are always separate concerns, implemented as reusable FastAPI dependencies,
  never as ad-hoc checks copy-pasted into route handlers.

## Postman documentation

- Every API endpoint gets an entry in the local Postman collection at
  `postman/native-life-api.postman_collection.json` — method, path, and its
  parameters (query/path/body), kept minimal: just enough for a quick manual
  check, not full prose documentation.
- Update the collection in the same change that adds/modifies an endpoint.
- Use the `{{base_url}}` collection variable instead of hardcoded hosts, so
  it works against local/staging without edits.
- The `postman/` folder is gitignored — it's a local working aid, not
  committed source. Never put real tokens/secrets in it even though it's
  git-ignored, since it can still end up shared ad hoc.

## Testing

- `tests/unit/` — no database, no network.
- `tests/integration/` — hits a real (test) database.
- New business logic gets a test. Don't rely on manual testing alone for
  anything beyond a UI/browser check.

## Workflow

- Work happens on feature/phase branches, not directly on `main`.
- Before any destructive git operation or one that discards uncommitted work,
  run `git status` first.
- Run `ruff check .`, `mypy app`, and `pytest` before considering a change
  complete.
